## 構想と方針
- ユーザーの構想：Windows Terminal はタブで複数のターミナルを 1 つのウィンドウにまとめられるが、この「タブでまとめたウィンドウ」をプロジェクトの数だけ束ねて管理したい。管理ツールの名前は wtbun
- ユーザーのシナリオ：
  - 最初の起動では wtbun の小さなウィンドウだけが出る
  - 「プロジェクトを開く」でフォルダを選ぶと、構成ファイルに従ってタブ付きの Windows Terminal のウィンドウを開く（なければ構成ファイルを作る）
  - プロジェクトはいくつでも開ける。全プロジェクトのウィンドウは同じ場所・同じサイズにそろえ、どれかのリサイズは全部に及ぶ
  - wtbun にはプロジェクトの一覧をタブで出し、選ぶとそのウィンドウが最前面に出る。並べ替え・閉じるもここから
  - wtbun を終了すると配下のウィンドウが全部閉じ、次に起動すると前回のプロジェクトを開き直す
- 調べたこと：Windows Terminal は `wt -w <名前>` で名前付きのウィンドウにタブを開ける。開いているタブの中身（数・フォルダ・実行中のコマンド）を外から読む公式の方法はない。全ウィンドウが 1 つのプロセスで動くので、プロセス ID ではウィンドウを見分けられない（起動の前後でウィンドウ一覧を比べて特定する）
- シナリオに足した点：ウィンドウを直接閉じられたときの検知、構成ファイルは「開くときの初期構成」になること、タスクバーの扱い、Windows Terminal の「前回のウィンドウを復元」設定とぶつかること
- ユーザーと決めたこと：
  - 言語は C# / WPF
  - wtbun のタブ列はターミナルのウィンドウの真上に吸着させる
  - 構成ファイルはプロジェクト直下の `.wtbun.json`
  - 管理下のウィンドウをタスクバーに出すかは設定で切り替える。初期値はコードが楽な方（出したまま）
- 環境：Windows Terminal 1.24.12741.0。.NET は 10 が RC1 しかなく、8・9 は 2026 年 11 月にサポートが終わるので、ユーザーが .NET SDK 10.0.403 と Visual Studio の更新を入れた
- 実装の順番：土台 → ウィンドウを開いて特定する → 切り替えと閉じる → 位置・サイズの連動と吸着 → 状態の保存と復元 → 設定

## 手順 1：土台
- 作ったもの：ソリューション `wtbun.slnx` と WPF プロジェクト `src/Wtbun`（net10.0-windows）、`.gitignore`
  - `MainWindow`：横長の小さなウィンドウに、プロジェクトのタブ列と「＋」（プロジェクトを開く）。タブの「×」で一覧から外す。タブにマウスを乗せるとフォルダを出す
  - 同じフォルダをもう一度開いたときは、タブを増やさず既にあるタブを選ぶ
  - `Config/ProjectConfig.cs`・`Config/ProjectConfigStore.cs`：`.wtbun.json` の読み書き。なければ `{ "version": 1, "tabs": [ { "dir": "." } ] }` を作る。タブの項目は `title`・`dir`（相対パスはプロジェクト基準）・`command`・`profile`。コメントと末尾のカンマを許す。タブが空なら既定のタブで補う（ファイルは書き換えない）。書式の誤りや読み書きできないときは、利用者向けのメッセージを出して開くのをやめる

- 確かめたこと：ビルド（警告は環境変数 LIB に残った古い VC98 のパスの 2 件だけ）、起動して wtbun のウィンドウが出ること。フォルダを選ぶ操作はまだ試していない

## 手順 2：ウィンドウを開いて特定する
- 調べたこと：今開いている Windows Terminal のウィンドウは、クラス名 `CASCADIA_HOSTING_WINDOW_CLASS` の 6 つで、全部同じプロセスだった（想定どおりプロセス ID では見分けられない）
- 作ったもの：
  - `Terminal/WtCommand.cs` の `Build`：構成から `-w <名前> new-tab -d ... --title ... -p ... <コマンド> ; new-tab ...` を組み立てる。`dir` は相対パスをプロジェクト基準で絶対パスにする。値は Windows の引数の規則で引用符に囲み（末尾の `\` も 2 倍にする）、`;` は `\;` にする。`command` は利用者の引用符を活かすためそのまま付ける
  - `Terminal/TerminalLauncher.cs` の `OpenAsync`：開く前に全ウィンドウを控え、wt.exe を起動し、100ms ごとに新しく表示されたウィンドウを探す（15 秒まで）。取り違えないよう、`SemaphoreSlim` で 1 つずつ開く。起動できない・見つからないときは `TerminalLaunchException`
  - `Terminal/TerminalWindows.cs`・`Native/NativeMethods.cs`：ウィンドウの列挙
  - `Project` に `WindowName`（`wtbun-` ＋ランダムな 12 桁。数字だけだと wt.exe がウィンドウ番号と見なすため接頭辞を付ける）と `WindowHandle`
  - `MainWindow`：タブを足してからウィンドウを開き、失敗したらタブを外してメッセージを出す
- 確かめたこと：ビルド。使い捨ての試験用プログラム（scratchpad）で、空白を含むフォルダに、タイトル `main` と `a;b`、`dir` が `.` と `src` の 2 タブを開くと、約 0.6 秒で新しいウィンドウを特定でき、UI オートメーションで読むとタブ名が `main`・`a;b`、選ばれている 2 つ目のタブの開始フォルダが `…\proj with space\src` になっていたこと。中のコマンドが終わるとウィンドウが閉じ、元の 6 つだけが残ったこと
- 試していないこと：wtbun の画面から「＋」でフォルダを選んで開く操作、`profile` の指定、wt.exe がないときのメッセージ
- タブの「×」は、今は一覧から外すだけで、ウィンドウは閉じない（手順 3 で作る）

## 手順 3：切り替えと閉じる
- 調べたこと：使い捨ての試験用プログラムで、Windows Terminal のウィンドウに WM_CLOSE を送ると、タブが 1 つならすぐ閉じてウィンドウハンドルもなくなる（IsWindow が false）。タブが 2 つだと「すべてのタブを閉じますか？」の確認が出て、ウィンドウは残る
- そこで「×」は閉じるよう求めるだけにし、タブはウィンドウが実際になくなったときに外すことにした。確認で取り消されたときも、利用者が Windows Terminal 側で閉じたときも、同じ仕組みで扱える
- 作ったもの：
  - `TerminalWindows` の `Activate`（最小化されていれば戻して SetForegroundWindow）・`RequestClose`（WM_CLOSE）・`Exists`（IsWindow）
  - `MainWindow`：タブを選ぶと（`ProjectTabs_SelectionChanged`）、また選ばれているタブをもう一度クリックしても（`Tab_MouseLeftButtonUp`）ウィンドウを前面に出す。同じフォルダをもう一度開いたときも前面に出す
  - `CloseProject`：ウィンドウを前面に出してから閉じるよう求める（確認が出たときに見えるように）。開いている途中は何もしない
  - `RemoveClosedProjects`：0.5 秒ごと（DispatcherTimer）に、ウィンドウがなくなったプロジェクトのタブを外す。`RemoveProject` で、選ばれていたタブなら隣を選ぶが、そのウィンドウは前面に出さない
  - 並べ替え：タブのドラッグ（`Tab_PreviewMouseLeftButtonDown`・`Tab_PreviewMouseMove`・`Tab_Drop`）と、右クリックのメニュー「左へ移動」「右へ移動」「閉じる」
- 確かめたこと：ビルド。UI オートメーションで wtbun を外から操作する使い捨ての試験（scratchpad）で、「＋」からフォルダを選んで 2 つのプロジェクト（alpha・beta）を開けること、タブ alpha → beta → alpha のクリックで、それぞれのウィンドウが前面に出ること、右クリックの「右へ移動」で並びが beta・alpha になること、beta の「×」でウィンドウが閉じてタブが外れること、alpha のウィンドウを外から閉じるとタブが外れること
- 試していないこと：ドラッグでの並べ替え、最小化したウィンドウを戻すこと、タブが複数のときの確認で「キャンセル」したときにタブが残ること

## 手順 4：位置・サイズの連動と吸着
- 決めたこと：最大化や上端に寄せたときは、真上にタブ列を置く場所がない。また、裏のウィンドウを前面に出さずに最大化する方法がない。そこで、ウィンドウの見えている枠は作業領域の上端からタブ列の高さより下にしか置かず、最大化は「タブ列の下の作業領域いっぱい」に置き換えて、もう一度最大化すると元に戻すことにした（ユーザーに伝えて進めた。合わなければ変える）
- 作ったもの：
  - `app.manifest`：PerMonitorV2 にして、物理ピクセルの座標で Windows Terminal に合わせる
  - `Native/WindowOps.cs`：位置・見えている枠（DWMWA_EXTENDED_FRAME_BOUNDS。GetWindowRect は見えない縁を含む）・作業領域・DPI・移動・元に戻すなど
  - `Native/WindowEventWatcher.cs`：Windows Terminal のプロセスの、前面化・移動の開始と終了・位置の変化を SetWinEventHook で受け取る
  - `Layout/TerminalLayout.cs`：共有の位置とサイズ（`SharedRect`）、タブ列の余白を空ける・最大化を置き換える `Normalize`、ほかのウィンドウを前面に出さずに合わせる `Apply`、タブ列の位置 `StripRect`
  - `MainWindow`：タイトルバーのない高さ 32 DIP のタブ列にした。右端の「≡」に「wtbun を終了」
    - 選ばれているウィンドウが動くとタブ列がついて行き、移動の終わり（または 0.2 秒止まったとき）に `SyncFrom` でほかのウィンドウをそろえる。wtbun がそろえたときのほかのウィンドウの変化は見ない
    - 直接前面に出されたウィンドウのタブを選び、タブ列を前に出す
    - タブ列の空いている所をドラッグすると、全ウィンドウを一緒に動かす
- 確かめたこと：ビルド。UI オートメーションの使い捨ての試験（scratchpad、拡大率 175%・DPI 168 のモニター）で、2 つのプロジェクトを開くと同じ位置とサイズになり、タブ列が見えている枠の真上に同じ幅で付くこと、選ばれているウィンドウを外から動かすともう 1 つもそろうこと、上端（y=0）に置くとタブ列の高さ（56px）だけ下にずれること、最大化で作業領域いっぱい（枠が 0,56〜3400,2160）になり、もう一度で元に戻ること、タブ列のドラッグ（+100,+50）で 2 つとも同じだけ動くこと、タブの切り替えでタブ列が付き直すこと
- 試していないこと：マウスでウィンドウの縁や上をドラッグしたとき（移動の開始と終了のイベント）、Win＋矢印キーでのスナップ、最小化、拡大率の違う複数のモニターをまたいだとき
- 「wtbun を終了」は、今は wtbun が終わるだけで、ウィンドウは閉じない（手順 5 で作る）

## 手順 5：状態の保存と復元
- 気づいたこと：終了時に全ウィンドウに WM_CLOSE を送っても、タブが複数あるウィンドウは Windows Terminal の確認で取り消されることがある（wt.exe にはウィンドウを閉じるサブコマンドもない）。そこで状態にウィンドウハンドルを保存し、次の起動でそのウィンドウが残っていれば新しく開かずに引き取ることにした（ユーザーに伝えて進めた）。wtbun だけが強制終了したときも元に戻る
- 作ったもの：
  - `Config/AppState.cs`・`Config/AppStateStore.cs`：`%APPDATA%\wtbun\state.json` の読み書き。開いていたプロジェクト（並び順・フォルダ・ウィンドウ名・ウィンドウハンドル）、選んでいたタブ、`SharedRect`、タブ列の位置。別のファイルに書いてから置き換える。読めなければ null（初めての起動と同じ）
  - `MainWindow`：
    - `RestoreAsync`（起動時）：タブ列と共有の位置を戻し（つながっていないモニターの上なら使わない）、プロジェクトを順に開き直して、選んでいたタブのウィンドウを前面に出す。開き直している間は、途中のタブのウィンドウを前面に出さず、保存もしない。フォルダが見つからないものはまとめてメッセージを出す
    - `OpenProjectAsync` に前回の状態を渡すと、残っているウィンドウ（`TerminalWindows.IsTerminalWindow`）を引き取る
    - `MarkStateChanged`：開く・閉じる・並べ替え・選ぶ・位置とサイズの変化のたびに、0.5 秒まとめて保存する。サインアウト・シャットダウン（SessionEnding）でも保存する
    - `CloseAllOnExit`（Closing）：保存してから、全ウィンドウに閉じるよう求める
  - `Project` から構成（`Config`）を外し、前回のウィンドウ名を引き継げるようにした
  - `RECT` の `Width`・`Height` は保存しない（JsonIgnore）
- 確かめたこと：ビルド。UI オートメーションの使い捨ての試験（scratchpad）で、
  - 2 つのプロジェクトを開いて beta を動かし、alpha を選んでから wtbun だけを強制終了すると、ウィンドウは残り、state.json に 2 つのプロジェクト・選択・位置が入っていること
  - 起動し直すと、新しく開かずに 2 つのウィンドウを引き取り（Windows Terminal のウィンドウの数が変わらない）、alpha が選ばれて前面に出て、タブ列が付くこと
  - 「wtbun を終了」で wtbun が終わり、2 つのウィンドウが閉じること
  - 起動し直すと、2 つのウィンドウが新しく開き、並び・選択・位置とサイズ（300,200〜1300,800）が戻り、alpha が前面に出てタブ列が付くこと
- 試験の途中で、前の試験で保存した状態から wtbun が試験用のプロジェクトを開き直していたため、試験が止まった（開き直しは動いていた）。残った wtbun に WM_CLOSE を送って終わらせ（Process.CloseMainWindow は WPF の別の隠れたウィンドウに送られて効かなかった）、試験で作った state.json を消した。Windows Terminal のウィンドウは元の 6 つに戻った
- 試していないこと：タブが複数あるウィンドウの閉じる確認で取り消したときの引き取り、フォルダが見つからないときのメッセージ、サインアウト・シャットダウン、モニターを外したとき

## 手順 6：設定
- 作ったもの：
  - `Config/AppSettings.cs`：`%APPDATA%\wtbun\settings.json`。今は `showTerminalsInTaskbar`（初期値 true）だけ
  - `Config/UserDataFile.cs`：`%APPDATA%\wtbun\` の JSON の読み書きを共通にした（`AppStateStore` もこれを使う）
  - `Native/Taskbar.cs`：ITaskbarList の AddTab・DeleteTab で、ほかのプロセスのウィンドウのタスクバーのボタンを出し入れする。エクスプローラーの再起動を知らせる TaskbarCreated メッセージ
  - `MainWindow`：「≡」に「ターミナルをタスクバーに表示」（チェック付き）。オフなら、開いた・引き取ったウィンドウのボタンを外す（`ApplyTaskbarSetting`）。切り替えたときは全ウィンドウに反映し（`ApplyTaskbarSettingToAll`）、TaskbarCreated でも外し直す。終了するときは、閉じる確認で取り消されて残ったウィンドウを選べるよう、ボタンを戻してから閉じる
  - `RaiseSelectedTerminal`：wtbun が前面に来たら、選ばれているウィンドウを wtbun のすぐ後ろまで持ち上げる（`WindowOps.PlaceBehind`。入力先は wtbun のまま）。タスクバーに出さないときでも、wtbun のボタンでターミナルが見えるように
- 確かめたこと：ビルド。このパソコンのタスクバーは画面の右に縦に置いた Open-Shell の形で、UI オートメーションでは実行中のボタンを読めず、写真ではボタンが多くてスクロールしていて見分けられなかった。MSAA（AccessibleObjectFromWindow で MSTaskListWClass）ならボタン名を読めたので、それで数えた。UI オートメーションの使い捨ての試験（scratchpad）で、
  - 開いた直後は alpha・beta のボタンが 1 つずつあり、オフにすると 0 になること、settings.json に false が入ること
  - wtbun を強制終了して起動し直し、引き取ったウィンドウもボタンが 0 のままのこと
  - オンに戻すと 1 つずつに戻ること
  - オフにして「wtbun を終了」すると、ウィンドウが閉じること
- 試験の途中で、起動直後に「＋」を押してもダイアログが開かず止まったことがある（起動から押すまでを 1.5 秒空けたら通った）。残った wtbun は WM_CLOSE で終わらせ、試験で作った settings.json・state.json は消した
- 試していないこと：wtbun が前面に来たときにウィンドウが持ち上がること、エクスプローラーの再起動、タスクバーに出さないときにウィンドウを最小化したときの見え方

## command のバッチファイル
- ユーザーの報告：`./.wtbun.toml` で試すと、「'npm run dev' の起動時にエラー 2147942402 (0x80070002) が発生しました 指定されたファイルが見つかりません。」と出た

- 原因：Windows Terminal はコマンドラインをそのまま CreateProcess に渡すので、拡張子のないプログラム名は `.exe` しか探さない。`npm` の実体は `npm.cmd`（`where npm` で `C:\Program Files\nodejs\npm.cmd` などを確かめた）で見つからない。`yarn`・`pnpm`・`code` なども同じ
- ユーザーと決めたこと：wtbun が自動で補う（ほかの案は、プロファイルのシェルの中で実行する（Windows Terminal の設定を読む必要があり大きい）、例と説明を直すだけ）
- 作ったもの：`Terminal/CommandLauncher.cs` の `Prepare`。先頭のプログラム名（引用符で囲んであればその中）を、タブの開始フォルダ・システムのフォルダ・Windows のフォルダ・PATH から探し、`.exe` がなく `.cmd`・`.bat` があれば（または拡張子が `.cmd`・`.bat` なら）`cmd /c "…"` で包む（cmd は最初と最後の引用符を外すので、中の引用符はそのまま渡る）。パスを含む名前は、その場所だけを探す。`WtCommand.Build` で使う。既定のファイルのコメントに「npm のようなバッチファイルもそのまま書ける」「コマンドが終わるとタブも閉じる」を足した。README・spec の例も `'npm run dev'` に戻した
- 作ってみて分かったこと：パスを含む名前（`bin\hello`）で、探すフォルダとファイル名の両方にパスを付けていて見つからなかった。ファイル名だけで探すよう直した
- 確かめたこと：Release でビルド（ユーザーが Debug の wtbun を動かしていて、Debug の実行ファイルを上書きできなかった）。一時フォルダーで使い捨ての試験用プログラムを動かし、`npm run dev`・`npm.cmd --version`・`"bin\hello.cmd" a b`・`bin\hello`・`npm run "a b"` が `cmd /c "…"` で包まれ、`git status`・`ping`・`cmd /c echo x`・見つからない名前はそのままのこと。実際に Windows Terminal で開いて、`npm --version` のタブに `11.5.2`、空白を含むフォルダーの `bin\hello.cmd` のタブに `hello-from-batch` が出ること。試験用のフォルダーは消した
- 試していないこと：wtbun の画面から、ユーザーの `.wtbun.toml` を開くこと（ユーザーの wtbun が動いていたため）
