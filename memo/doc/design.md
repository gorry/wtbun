# 設計方針

wtbun の方針と、そう決めた理由。機能の詳細は [spec.md](spec.md)。

## 目的
Windows Terminal はタブで複数のターミナルを 1 つのウィンドウにまとめられる。wtbun は、この「タブでまとめたウィンドウ」をプロジェクトの数だけ束ねて管理する。

- プロジェクトごとに 1 つの Windows Terminal のウィンドウを開く
- 全プロジェクトのウィンドウを同じ場所・同じサイズにそろえ、wtbun のタブで切り替える
- wtbun を閉じると全部閉じ、次に起動すると前回のプロジェクトを開き直す

## 構成

```
wtbun（WPF）
 ├ タブ列（ターミナルのウィンドウの真上に吸着）
 ├ プロジェクト直下の .wtbun.toml を読み、wt.exe -w <名前> new-tab ... で開く
 ├ Win32 API でウィンドウを特定・前面表示・移動・リサイズ・監視
 └ 開いていたプロジェクトを %APPDATA%\wtbun\ に保存
        │
        ▼
Windows Terminal（プロジェクトごとに 1 ウィンドウ）
```

## 決めたことと理由

### C# / WPF
- ウィンドウの列挙・前面表示・移動・監視（WinEvent フック）といった Win32 API を呼びやすい
- タブ付きの小さな画面をすぐ作れる。単一の exe で配れる
- .NET 10（長期サポート版）を使う。8・9 は 2026 年 11 月にサポートが終わる

### Windows Terminal は wt.exe で操作する
- `wt -w <名前>` で名前付きのウィンドウにタブを開ける。`new-tab`・`split-pane` を `;` でつなげば、構成を一度に開ける
- 開いているタブの中身（数・フォルダ・実行中のコマンド）を外から読む公式の方法はない。そのため「今の状態を保存する」のではなく、「決めておいた構成を開く」形にする

### 開いたウィンドウは、起動の前後のウィンドウ一覧を比べて特定する
Windows Terminal は全ウィンドウを 1 つのプロセスで動かすので、プロセス ID では見分けられない。

### 構成ファイルはプロジェクト直下に置く
`.wtbun.toml` をプロジェクトと一緒に git で管理・共有できる。中身は「開くときの初期構成」で、開いた後に手で増やしたタブは反映されない。

### 構成ファイルは TOML で書く
- 利用者が手で書き換えるので、コメントを書ける形式にする
- Windows のパスやコマンドは `\` と `"` を多く含む。TOML の `'…'`（リテラル文字列）なら、エスケープせずにそのまま書ける（JSON・JSONC は毎回エスケープが要る）
- 字下げに意味がないので、YAML より書き間違えにくい。タブの一覧も `[[tabs]]` を並べて素直に書ける（INI は繰り返しが苦手）
- 読み込みには Tomlyn（BSD-2-Clause）を使う。知らない項目を黙って読み飛ばすので、書き間違いに気づけるよう、項目名は自分で確かめる
- 最初に作るファイルには、README を読まなくても書き換えられるよう、説明と例をコメントで入れる
- タブの分割は、タブの中に `[[tabs.panes]]` を並べて書く。wt.exe の split-pane は「直前のペインを分割する」並びで指示するので、その順のまま書けるようにした（木の形で書かせると、wt.exe の指示に直すのに手間がかかり、書く人も分かりにくい）
- 分割の向きは wt.exe の `-V`／`-H`（vertical・horizontal）ではなく、新しいペインを置く向き（`right`・`down`）で書く。vertical がどちらの向きかは取り違えやすい。Windows Terminal の設定の splitPane の書き方とも同じ
- 値の名前は Windows Terminal の設定の名前に合わせる（`tab_color`・`color_scheme`・`suppress_application_title` など）。Windows Terminal の説明書と照らし合わせやすいように

### 構成ファイルへの書き戻し
- 手で書きたくない人のために、ダイアログで編集できるようにする。wtbun が構成ファイルに書き戻すのは、利用者がこのダイアログで保存したときだけ（開いた後に増やしたタブなどを、自動で書き戻すことはしない）
- 手で書く人とダイアログを使う人が同じファイルを使えるよう（git で共有もできるので）、ファイル全体を作り直さず、変わった所だけを置き換えて、コメントをなるべく残す
- タブの部分はまとめて書き直す。並べ替えや削除をすると、タブの間のコメントがどのタブのものか決められないため。コメントが消えるときは、保存の前に確認する
- 書いた結果を読み直し、編集した内容にならなければ書き込まない。珍しい書き方のファイルを壊さないため

### タブ列はターミナルの真上に吸着させる
全プロジェクトのウィンドウが同じ場所に重なるので、その上にタブ列を貼り付けると、ブラウザのタブのように切り替えられる。

### 最大化は「タブ列の下の作業領域いっぱい」に置き換える
- 本当に最大化すると、真上にタブ列を置く場所がない
- 裏のウィンドウを前面に出さずに最大化する方法がない（ShowWindow の最大化は前面に出す）
- そこで、ウィンドウはいつも普通の状態のまま、同じ位置とサイズにそろえる。最大化されたら作業領域いっぱいの大きさに直し、もう一度最大化されたら元に戻す

### 残っているウィンドウは、次の起動で引き取る
- 終了時に全ウィンドウを閉じても、タブが複数あるウィンドウは Windows Terminal の確認で取り消されることがあり、確実には閉じられない（wt.exe にはウィンドウやタブを閉じるサブコマンドがない）
- そこで状態にウィンドウハンドルも保存し、次の起動でそのウィンドウが残っていれば、新しく開かずにそのまま使う。wtbun だけが強制終了したときも、同じ仕組みで元に戻る
- Windows Terminal は閉じる確認を同時に 1 つしか出さず、確認が出ている間のほかのウィンドウへの閉じる求めを無視する。そこで終了時は、ウィンドウを 1 つずつ閉じ、閉じるか確認が取り消されるまで待ってから次へ進む（wtbun はそれまで終わらない）
- 確認が出ているかは、UI オートメーションで確認の「すべて閉じる」ボタンを、表示の文字ではなく AutomationId（`PrimaryButton`）で探して見分ける。表示の言語によらず、タブの「タブを閉じる」ボタン（`CloseButton`）とも取り違えない。外から確認を調べる API はほかにない

### タブ列とターミナルは、前面になったときに並べ直す
タブ列（wtbun）とターミナルは別のプロセスのウィンドウなので、片方が前面になっても、もう片方はほかのアプリの後ろに残る。そこで、前面になったという知らせ（EVENT_SYSTEM_FOREGROUND・wtbun の Activated）を受けて、もう片方を前に出す。

- 前面にいないプロセスから HWND_TOP でいちばん上に置く指示は、Windows に無視される
- 前面になったウィンドウの「すぐ後ろ」に置く指示は効くが、置く側が Windows Terminal のウィンドウだと、すぐ後ろではなく上に来てしまう。そこでどちらも、いったん最前面指定にしてからすぐ外す方法で持ち上げる
- タブ列はターミナルより上に置く。後ろに置くと、「ウィンドウの下に影を表示する」が有効なときに、ターミナルの影がタブ列に落ちて暗くなる。影はウィンドウの外の後ろ側にしか落ちないので、上に置けば暗くならない
  - タブ列を常に最前面にする案は、ほかのアプリの上に出続けるのでやめた。タブ列をターミナルの所有ウィンドウにする案は、ターミナルを閉じるとタブ列も破棄されるのでやめた
- 知らせの時点では、前面になった方がまだいちばん上に上がりきっていないことがあるので、少し待ってもう一度置き直す

### 最小化はまとめて行う
全プロジェクトのウィンドウは同じ場所に重なっているので、1 つだけ最小化すると、すぐ後ろのウィンドウが現れて最小化できていないように見える。そこで、選ばれているウィンドウの最小化を知らせ（WinEvent）で受けて、タブ列と全ウィンドウを最小化する。

- ShowWindow でほかのプロセスのウィンドウを最小化すると、最小化されたウィンドウが前面に残り、入力が見えないウィンドウに入ることがあった。後から外す方法も効かなかった。そこで `SC_MINIMIZE` をウィンドウに送って、最小化ボタンと同じくウィンドウ自身に処理させ、前面になったウィンドウから順に最小化して、前面の受け渡しを Windows に任せる
- 最小化ボタンを横取りする方法（別プロセスのウィンドウへのフックの注入など）は、壊れやすいので使わない。最小化が始まった知らせを受けるだけなので、Windows Terminal の作りに依存しない

### 閉じるボタンと Alt+F4 は入力の段階で止める
閉じる前に確認を出すには、閉じ始めた知らせを受けるのでは遅いので、入力がウィンドウに届く前に止める必要がある。

- タスクバーから閉じる操作は入力ではなく、タスクバーからウィンドウへ直接メッセージが届くので、この方法では止められない（次の節）
- 低レベルフック（WH_MOUSE_LL・WH_KEYBOARD_LL）を使う。別プロセスへの注入がいらず、wtbun が終わればフックも消える
- ボタンの位置は持たず、ウィンドウ自身に WM_NCHITTEST で尋ねる。UI オートメーションと違ってすぐ答えが返り（フックの中で呼べる）、拡大率やボタンの並びに依存しない
- 答えが得られなければクリックを通す。今後の Windows Terminal で答え方が変わっても、確認が出なくなるだけで閉じるボタンは使える
- フックはマウス全体の入力に関わるので、UI スレッドが忙しくても操作を遅らせないよう、専用のスレッドで受ける
- wtbun は前面にいないので確認を前面に出せない。確認の直前だけ AttachThreadInput で前面のスレッドと入力の状態を共有して、前面に出す（`WindowOps.TakeForeground`）

### タスクバーから閉じる操作は DLL の注入で止める
別プロセスのウィンドウに届くメッセージを止めるには、そのプロセスの中でコードを動かすしかない。最小化では注入を避けた（知らせを受けるだけで足りたため）が、閉じる操作は閉じてからでは遅い。ユーザーと相談して、`SetWindowsHookEx` で DLL を読み込ませる方法に決めた。ほかの案は、タスクバーのボタンを隠す設定に任せる（設定がオンの人を救えない）、タスクバーの画面を監視する（Windows の更新で壊れやすい）。

- Windows Terminal は全ウィンドウが 1 プロセスなので、DLL が落ちると無関係のウィンドウも落ちる。そこで DLL は止める・知らせる・通すことだけをする。確認は wtbun 側で出し、DLL の中で待たない
- 失敗したときは閉じられる側に倒す。閉じられなくなるより、確認が出ない方がましなため（wtbun がいない、応答しない、DLL がない）
- フックが外れるとシステムは DLL をアンロードするので、wtbun の強制終了でサブクラスの処理先が消えないよう、サブクラスごとに DLL の参照を持つ。手放すのは、処理を抜けたころに別スレッドで行う（`FreeLibraryAndExitThread`）
- 閉じるボタンと Alt+F4 は、Windows Terminal の中で処理されて `WM_CLOSE` を通らないと見込み、入力の段階で止める方法を残した（通るかは試していない）

### 座標は物理ピクセルでそろえる
wtbun はモニターごとの DPI に対応させ（`app.manifest` の PerMonitorV2）、位置とサイズは Win32 API の物理ピクセルで扱う。Windows Terminal も同じなので、拡大率が 100% でないモニターでも、ずれずにそろえられる。

### タスクバーの表示は設定で切り替える
初期値は Windows Terminal の通常の動き（プロジェクトの数だけ並ぶ）。管理下のウィンドウを隠して wtbun だけを出す設定も用意する。

- 隠すのは ITaskbarList の DeleteTab で行う。ほかのプロセスのウィンドウにも使え、見た目や Alt＋Tab は変わらない（WS_EX_TOOLWINDOW に変えると、見た目と Alt＋Tab も変わる）
- 隠したときは、wtbun のボタンからターミナルにたどり着けるよう、wtbun が前面に来たら選ばれているウィンドウも一緒に持ち上げる

## 気をつけること
- Windows Terminal の「前回のウィンドウを復元」設定が有効だと、wtbun の復元と二重に開く。オフにしてもらうよう案内する
- 閉じるときに Windows Terminal の「すべてのタブを閉じますか？」確認が出ることがある
- 利用者がウィンドウを直接閉じたときは、wtbun が気づいて一覧に反映する

## アプリ名・バージョン
アプリ名・略名・バージョン・著作権表示などの定数は、リポジトリ直下の `Profile.ini` にまとめてある。このファイルは著作者だけが書き換える（プログラムや AI は読むだけ）。コードには直接書かず、ビルドのときに `Profile.ini` から作る `AppProfile` を使う。

- MSBuild の `Directory.Build.props`・`Directory.Build.targets` で読むので、ほかの道具（スクリプトなど）は要らない。Visual Studio でも `dotnet build` でも同じに動く
- 使い方は [spec.md](spec.md) の「アプリ名・バージョン（Profile.ini）」

### クリップボードへのコピー
- WPF の `Clipboard.SetText` は使わず、Win32 の API で文字列をその場で置く（`ClipboardText`）
- `Clipboard.SetText` は、中身を後から渡す形（OLE の遅延レンダリング）で登録してから、すぐに確定（`OleFlushClipboard`）しようとする。クリップボードを見張るアプリ（UltraVNC の vncviewer など）がその間に中身を読もうとすると、そのアプリはクリップボードを開いたまま wtbun の返事を待ち、wtbun は確定のために待っていて返事ができない。お互いに待って、何度やり直しても失敗する（`CLIPBRD_E_CANT_OPEN`）
- 中身をその場で置けば後から渡す必要がないので、見張っているアプリが読みに来ても待ち合いにならない
